# 进球 / 扑救检测模型训练计划

## 1. 背景与问题定义

- 现状：`experimental/` 下已尝试基于**静止画面 + 手工特征**（帧差、光流、跟踪、两端占用率）检测进球与扑救，成功率约 **10%**，不达可用标准。
- 静态分析失效的根本原因：进球/扑救是**时序事件**，关键信号在"射门动作/球的轨迹/守门员反应"的运动过程与上下文（回放机位、球员聚集反应）中，单帧外观信息量不足。
- 目标：训练一个有**时序建模**能力的模型，输入视频片段，输出进球(goal)与扑救(save)发生的时间点，替代/大幅超越 10% 的静态基线。

### 任务分类
本问题属于 **Temporal Action Detection / Action Spotting**（时序动作检测），二分类场景：`goal`、`save`。

---

## 2. 技术路线（重要先决判断）

> 先回答"这东西到底要不要上深度模型"。**别急着写模型**，路线 C 可能一天就超过 10%。

| 路线 | 做法 | 训练成本(本机) | 预期增益 | 建议 |
|---|---|---|---|---|
| C. 手工特征 + 浅分类器 | 复用现有帧差/光流特征 + 音频噪声爆发（进球欢呼/哨声）+ 回放/机位切换，喂给 GBDT/MLP | 几小时 | >10%，立即可测 | **第 1 步必做**，用来量化"模型到底要补多少" |
| A. 特征 + 时序定位头 | 开箱即用的深度特征（SoccerNet 预提取特征）+ GRU/Transformer 头做事件定位 | 1–2 天 | F1 30–60% 常见 | **第 3 步默认选**，不训练视频主干 |
| B. 端到端视频模型 | 微调 Kinetics400 预训练的轻量视频模型(X3D-M / VideoMAE-Small) | 2–4 周 | 上限更高，数据需求大 | 第 3 步之后按需升级 |

策略：**C 当基线 → A 拿结果 → B 兜底**。不要一上来就端到端。

## 3. 硬件评估

### 现有机器足够吗？——足够跑路线 A 和 B(小模型)

| 组件 | 你的配置 | 对训练的影响 |
|---|---|---|
| GPU | RTX 3060 6GB | 能跑 fp16、224px、batch 4–8 的小视频模型微调；**装不下**大模型(TimeSformer-L/VideoMAE-L)与大分辨率(448px+大 batch) |
| CPU | i9-12900 | 视频解码/抽帧瓶颈在这里；可开 8–16 路并行抽帧，够用 |
| RAM | 16GB | 最紧的约束：**禁止整段视频加载内存**，必须用 ffmpeg 管道流式读帧（`experimental/motion_common.py:frame_reader` 已是此模式，可复用） |
| 磁盘 | 100GB 空闲 | 关键约束，见 §3.1 数据量预算 |

### 3.1 磁盘预算（100GB 怎么分）

| 内容 | 大小 | 说明 |
|---|---|---|
| 比赛视频(720p h264) | 每场约 1.5–2GB | 100GB 约可存 **40–50 场**，够路线 A/B 起步 |
| SoccerNet 预提取特征 | 约 22GB | 若走路线 A 的"特征版"，一次性下载，**不含原始视频** |
| 抽帧/特征缓存 | 10–20GB | 训练管线中间产物 |
| 模型权重/日志 | <5GB | 忽略不计 |
| **合计** | ≤70GB | 留 30GB 余量给系统与缓存 |

⚠️ SoccerNet 原始视频约 500GB，**放不下**，别走下载原始视频的路，只用它的标注+特征，或干脆自建数据。

### 3.2 推荐配置（若之后想上大档）

| 场景 | 建议 |
|---|---|
| 本地路线 A/C | 现有机器零投入 |
| 本地路线 B 加速 / 更大分辨率 | RTX 4070 Ti SUPER 16GB 或 RTX 4090 24GB |
| 云端路线 B | 租 A10 / L4 (24GB) 按小时算，训练完即释放（比买卡划算） |
| 备用存储 | 加一块 ≥200GB SSD/HDD 存原始视频 |

## 4. 分步实施计划

### Step 0 — 数据准备与标注（1–2 周，可与其余并行）
全程最大瓶颈，先启动。

- **动作**：
  1. 选定数据来源：(a) 下载 SoccerNet 标注与特征（推荐先做路线 A）；(b) 同时自建：下载 20–30 场正规足球比赛视频。
  2. 写一个极简标注工具：遍历比赛回放，记录事件时间戳，输出 `events.json`：`[{"video":..., "events":[{"class":"goal|save", "t_sec":...}]}]`。
  3. 用现有规则检测(`experimental/`)先自动生成候选时间点 → 人工只确认/修正候选，把标注成本降 80%。
- **产出**：≥20 场已标注数据；或 SoccerNet 特征+标注就绪。
- **验收**：`events.json` 能被一条脚本读取并打印统计（每类事件数）。

### Step 1 — 环境搭建 + 清洗基线（1–2 天）
- **动作**：
  1. 建 Python 环境：`python 3.11` + `pytorch 2.x (cu118)` + `torchvision` + `opencv-python` + `numpy`。
  2. 把 `experimental/` 各 solution 的静态检测结果在**真实比赛**上重跑一遍，统一评估脚本，记录精确基线（预期 ~10%）。
  3. 加一版最便宜的时序特征试水：候选窗口内 帧差能量 + 音频噪声爆发 + 回放/机位切换，喂给 `sklearn.ensemble.HistGradientBoostingClassifier`。
- **产出**：统一评估脚本 `eval.py`（输入候选时间戳 vs GT，输出 P/R/F1）+ 一份基线报告。
- **验收**：基线数字稳定复现；能回答"模型还需要补多少"。
- **ponytail:** 若浅分类器已明显 >10%（例如 >35% F1），先深入它，此阶段不写深度模型。

### Step 2 — 特征/数据管线（3–5 天）
- **动作**：
  1. 抽帧：滑动窗口每 1s 一簇 × 16 帧，逐场流式抽取（ffmpeg 管道，复用 `frame_reader`），多进程并行。
  2. 路线 A：接入 SoccerNet 预提取特征（或自提 ResNet 视频特征，仅推理，6GB 无压力）。
  3. 路线 B 预留：把 16×224×224 帧存 `h5/npy`，batch 式读取（`torch.utils.data.DataLoader`）。
  4. 类别均衡：goal/save 在整场中占比 ~1%，为正样本做**窗口内重采样**或**oversample**。
- **产出**：可复现的特征缓存 + `Dataset.py` + 一个可视化脚本确认抽帧与标注时间对齐。
- **验收**：抽 10s 片段可视化，确认时间戳对齐无偏移。

### Step 3 — 训练模型
**路线 A（默认，3–7 天）**
- 输入：每窗口深度特征序列；模型：`GRU(128–256)` 或 `4 层轻量 Transformer` 作时序头。
- 损失：`focal loss`（类不均衡）+ 时间定位项（spotting loss）。
- 训练：batch 256–512，AdamW，30–60 epoch，早停。
- 验收：验证集 goal F1 ≥ 0.4。

**路线 B（可选升级，2–4 周）**
- 微调 `X3D-M` 或 `VideoMAE-Small`（Kinetics400 预训练），输入 16×224×224。
- 本机配置（6GB 显存预算，务必照做）：
  - 混合精度 `(fp16)`，`batch=4`（大过 8 就爆显存）
  - `gradient accumulation` 攒到等效 batch 16–32
  - `lr 1e-4`，`~30 epoch`，`224px` 起步，调顺再试 320px
  - 难例挖掘：易错的非事件窗口进下一轮训练
- 验收：goal/save F1 相对路线 A 有提升，且值得其部署成本；否则留用 A。

### Step 4 — 时序后处理（2–3 天）
- **动作**：模型输出置信度曲线 → 平滑 → 峰值检测 → **时序 NMS**（同一事件相邻窗口合并）→ 设定阈值 → 输出事件时间戳列表 `[start, end]` 或单点 `t`。
- **验收**：单场样例中，进球被检出且时刻偏差 <2s；漏检率单独统计（漏检比误检更伤用户信任）。

### Step 5 — 集成进 highlight-creator（3–5 天）
- **动作**：
  1. 固化推理脚本：输入 `input.mp4` → 输出 `events.json`（CLI 形式，先离线）。
  2. 对接现有 `experimental/cutter.py` / 后端：候选时间戳直接进切片段流程。
  3. 若追求实时，再把模型导出 `ONNX/TRT`（6GB 可跑 fp16 推理）——**先不做，离线足够**。
- **验收**：一条命令行 `detect.py match.mp4 -o out/events.json` 出完整高亮候选列表。

### Step 6 — 真实比赛评估与迭代（1 周+）
- **动作**：在**未参与训练的 5–10 场**真实比赛上跑完整流程。
- **指标**：按 §5，goal 与 save 分开报 F1。
- **迭代策略**（重要）：先加数据，后调参。性能卡住 → 加 5–10 场标注数据 > 改超参 > 换模型。路线 A→B 的升级只在数据已充分时才有意义。
- **验收**：goal F1 ≥ 0.5 且时刻偏差 <2s 为可用线；≥0.7 为良好线。

## 5. 评估指标

| 指标 | 定义 | 目标 |
|---|---|---|
| 事件级 F1 | 预测事件与 GT 窗口 `IoU ≥ 0.5` 算命中 | goal F1 ≥ 0.5（起步）/ 0.7（良好），save 单报 |
| 定位偏差 | 预测时刻与 GT 中心时刻差值（秒） | goal 偏差 < 2s |
| 漏检率 | GT 中有、未检出的比例 | 单独监控，尽量压低 |
| 对比值 | 与 Step 1 的 ~10% 静态基线比 | 必须显著超越 |

`save` 类别样本更少、动作更弱，允许 F1 比 goal 低一档，但必须单独报告，不许合并掩盖。

## 6. 时间表（乐观估计）

| Step | 内容 | 耗时 | 关键产出 |
|---|---|---|---|
| 0 | 数据获取+标注 | 1–2 周 | ≥20 场标注 / SoccerNet 就绪 |
| 1 | 环境+基线 | 1–2 天 | 评估脚本 + 基线报告 |
| 2 | 特征管线 | 3–5 天 | 特征缓存 + Dataset |
| 3 | 训练（A 默认 / B 升级） | 1–4 周 | 可部署的检测模型 |
| 4 | 时序后处理 | 2–3 天 | 事件时间戳输出 |
| 5 | 集成 app | 3–5 天 | `detect.py` CLI 接入 cutter |
| 6 | 真实评估+迭代 | 1 周+ | 达标或回炉 |

**合计（路线 A）约 4–6 周**；端到端路线 B 另加 2–4 周。总时长主要由数据标注决定。

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| 数据不足 / 标注噪声（最大风险） | 用小数据先跑通全链路；用 SoccerNet 预训练特征迁移；候选自动预筛降低标注工作量 |
| 6GB 显存装不下大模型 | fp16 + 梯度累积 + 保守 batch；大模型上云(§3.2) |
| 类别极度不均衡（goal~1%） | focal loss + 重采样 + 难例挖掘 |
| 视频来源多样（机位/画质/比赛项目） | 全程只使用足球比赛数据一致训练；别混入其他运动 |
| 检测偏慢 | 先离线；需求实时时再 ONNX/TRT 导出 |
| 路线 A/B 超出需求 | 先做完 Step 1，若浅分类器已达标，深度模型整段跳过（YAGNI） |

---

## 8. 一句话结论

**别越过 Step 1。** 先量化基线，走**路线 A（特征+时序头）**用现有 3060 就能跑到可用的 F1；6GB 显存/16GB 内存不是阻碍，**100GB 磁盘与训练数据才是真正的瓶颈**；数据不够时优先加数据，而不是加模型。
